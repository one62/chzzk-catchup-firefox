# 실제 Firefox 탭의 60초 측정

> 0.3.3~0.3.4에서 사용한 조사 절차입니다. 0.3.5에서는 60초 측정 기능과 UI를 제거했습니다. 기존 진단 로그 JSON 저장은 남아 있습니다.

1. about:debugging에서 이 확장을 다시 로드하고 방송 탭을 새로고침한다.
2. 방송이 안정적으로 재생되면 F12 → 네트워크를 열고 기존 요청 목록을 지운다. 속도 제한은 사용하지 않는다. 캐시 설정과 화질·따라잡기 설정은 평소 상태를 유지한다.
3. 확장 팝업에서 **60초 측정 시작**을 누르고 팝업을 닫는다.
4. 처음 약 20초는 그대로 시청한다. 그다음 다른 프로그램으로 포커스를 옮기고 Codex 요청 등 평소 끊김을 유발하던 동작을 수행한다. 마지막에는 Firefox로 돌아온다.
5. 60초가 지나면 같은 방송 탭에서 팝업을 열어 **측정 JSON 저장**을 누른다. 네트워크 도구에서도 **모두 HAR로 저장 / Save All as HAR**를 선택한다.
6. JSON과 HAR를 함께 분석한다. 대략 몇 초쯤 어떤 동작을 했는지 덧붙이면 좋다. HAR에는 요청 URL·인증 쿼리·헤더 등이 포함될 수 있으므로 공개 저장소에는 올리지 않는다.

측정 중에는 새로고침하거나 방송을 바꾸지 않는다. 기록은 탭 메모리에만 보관되며 새로고침하면 사라진다. 다시 측정하면 이전 측정이 교체된다. 팝업을 닫거나 다른 창으로 전환해도 측정은 계속되지만, 페이지가 정지되면 실제 종료 콜백이 늦을 수 있다.

## 분석 방법과 한계

- samples.t는 측정 시작 기준 밀리초, wallTimeMs는 HAR 시간과 맞추기 위한 PC 시각이다. PC 시계가 바뀌면 단조 시간 t를 우선한다.
- 100ms 간격으로 currentTime, buffered, forwardBuffer, playbackRate, readyState, 누적 droppedFrames/totalFrames와 포커스·표시 상태를 기록한다. intervalMs가 커지면 타이머 실행이 지연된 것이다. 정확한 버퍼 추가 시점은 샘플 사이에 있다.
- resources는 Resource Timing에서 관측된 완료 요청이다. URL 대신 호스트·종류·시각만 저장한다. 교차 출처 제한으로 자세한 시간이 감춰지면 detailAvailable=false와 null로 기록한다. worker 내부 요청이나 진행 중 요청은 누락될 수 있다. 기록이 없다는 사실은 통신이 없었다는 뜻이 아니다.
- HAR에서 활성 미디어 목록의 EXTINF, EXT-X-PART, PART-TARGET, 요청 간격과 응답 시간을 확인한다. LL-HLS의 서버 대기는 새 영상 생성을 기다리는 정상 동작일 수도 있다.
- 영상 데이터 요청 완료와 버퍼 증가를 대조한다. 버퍼가 소진되며 waiting이 생기는지, 버퍼가 충분한데 누락 프레임만 늘어나는지 구분한다. 이 기록만으로 CPU/GPU/드라이버 원인을 확정하지 않는다.
- 수집기는 재생 속도나 네트워크 요청 방식을 변경하지 않는다. 측정 자체와 개발자 도구에도 약간의 부하는 있다. 서버로 자동 전송하지 않는다.
